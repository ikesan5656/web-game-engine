# Issue 対応

全体の流れは次のとおり。各工程は対応するサブエージェントに任せ、メインはその結果をまとめてユーザーとやり取りする。

| 工程       | 担当                                                                                                    |
| ---------- | ------------------------------------------------------------------------------------------------------- |
| ① 要件定義 | `doc-reviewer`                                                                                          |
| ② 設計     | `planner`                                                                                               |
| ③ 実装     | `implementer`（コード）・`doc-writer`（ドキュメント）を並行                                             |
| ④ レビュー | `code-reviewer`・`quality-checker`・（ドキュメント変更時）`doc-reviewer` を並行。軽微ならレビューを省く |
| ⑤ 動作確認 | メイン（lint・フォーマット確認のみ）＋ユーザーへの UI 確認依頼                                          |

**ドキュメント（`*.md`、`docs/`、`.claude/` 配下など）の作成・更新はメインや `implementer` では行わず、必ず `doc-writer` に任せる。ドキュメントを変更したときは、どの工程でも `doc-reviewer` を他のエージェントと並行して必ず起動する（④で軽微な修正としてレビューまたは再レビューを省くときを除く）。**

## 共通ルール

どの工程でも次に従う。

- **工程の区切り**: 各工程（①〜⑤と PR 作成）の終わりに、結果の要約をユーザーに見せて確認し、了承されてから次の工程に進む。修正を求められたら、その工程の中でやり直す
- **判断が必要なとき**: 要件の解釈、設計の選択肢、未コミットの変更の扱い、戻り先の工程など、判断が必要なときは AskUserQuestion で複数の案を示してユーザーに選んでもらう。推奨案があれば先頭に置き、「（推奨）」を付ける
- **進捗の記録**: 工程に入ったとき・工程を終えたとき・戻り先へ戻ったときに、「Issue の進捗記録」に従って Issue を更新する
- **戻ったときの記録**: 前の工程に戻るときは、戻る元の工程コメントに戻る理由と戻り先を追記する。戻り先の工程コメントは、やり直した結果で上書きする

## Issue の進捗記録

Issue の進捗は、工程ごとのコメント（工程コメント）と、本文の最上部のステータス欄の 2 つで記録する。Issue の本文とコメントはリポジトリのドキュメントではないので、`doc-writer` に任せずメインが書く。

`gh api` は、自分の工程コメントの更新（`issues/comments/<id> -X PATCH`）にだけ使う。コメントの削除（`-X DELETE`）、Issue のクローズ、ラベルや担当者の変更など、それ以外の操作には使わない。必要になったらユーザーに確認する。`gh api` は、パスを先に書き、`-X PATCH` などのオプションは後ろに書く。パスはダブルクォートで囲まない（allowed-tools ではクォートなしのパスの前方一致で許可しているため）。`{owner}/{repo}` は gh が自動で置き換えるので、そのまま書く。置き換えられないとき（リモートが複数あり、`gh repo set-default` が未設定のときなど）は、ユーザーに知らせて止まる。

Issue・PR の本文やコメントは、`mktemp` を使わず Write ツールでセッションのスクラッチパッドディレクトリ（システムプロンプトにあるもの）に書き出す。ファイル名は毎回新しくし、そのパスを `--body-file` や `-F body=@` に渡す。

### 工程コメント

工程ごとにコメントを 1 件だけ持つ。同じ工程で内容が変わったとき（④の修正ループ、戻り先からのやり直しなど）は、新しいコメントを足さずにその工程のコメントを更新する。

| 工程       | 工程ID           |
| ---------- | ---------------- |
| ① 要件定義 | `requirements`   |
| ② 設計     | `design`         |
| ③ 実装     | `implementation` |
| ④ レビュー | `review`         |
| ⑤ 動作確認 | `verification`   |
| PR 作成    | `pr`             |

1. コメントの本文を作る。先頭行に `<!-- issue-skill:phase=<工程ID> -->` を入れ、続けて工程名・結果の要約・ユーザーの判断・次の工程を書く
2. 本文をスクラッチパッドのファイル（以下「一時ファイル」）に書き出す
3. `gh issue view <番号> --json comments --jq '.comments[] | select(.viewerDidAuthor and (.body | startswith("<!-- issue-skill:phase=<工程ID> -->"))) | .url | split("#issuecomment-")[1]'` で、自分が書いたコメントのうち、先頭がマーカーのものの id を取り出す（コメントの URL の `#issuecomment-` の後ろが id）。複数出たら最初の 1 件を使う
4. id が出たら `gh api repos/{owner}/{repo}/issues/comments/<id> -X PATCH -F body=@<一時ファイル>` で上書きする。出なければ `gh issue comment <番号> --body-file <一時ファイル>` で追加する

### ステータス欄

本文の最上部に、次の形で置く。

```markdown
<!-- issue-skill:status:start -->

**ステータス**: ③ 実装中

**要約**: 確定した要件を 2〜3 行で書く

- [x] ① 要件定義
- [x] ② 設計
- [ ] ③ 実装
- [ ] ④ レビュー
- [ ] ⑤ 動作確認
- [ ] PR 作成

**作業ブランチ**: （③で作成後に書く）

**PR**: （作成後にリンクを書く）

<!-- issue-skill:status:end -->
```

- ステータスは「① 要件定義中」「① 要件定義済み」「② 設計中」「③ 実装中」「④ レビュー中」「⑤ 動作確認中」「PR 作成済み」のどれかにする。PR のマージ後のステータス更新は、このスキルの範囲外とする
- チェックリストは終えた工程に印を付ける。工程コメントへのリンクを付けてもよい。戻り先へ戻ったときは、やり直す工程から後の印を外す
- 要約は要件が確定してから書く。それまでは「（要件の確定後に書く）」としておく

更新の手順:

1. `gh issue view <番号> --json body -q .body` で本文を取る
2. マーカーで囲まれた欄だけを差し替える。欄がなければ本文の先頭に挿入する。残りの本文（テンプレートの内容）は変えない
3. 新しい本文を一時ファイルに書き出し、`gh issue edit <番号> --body-file <一時ファイル>` で更新する

## 0. 引数の確認

- $ARGUMENTS に Issue 番号または URL があれば、「① 要件定義」の「A. 既存 Issue」に進む。
- $ARGUMENTS が空なら、作業を始めずにユーザーに次のどちらかを聞く。判断の助けとして `gh issue list --state open --limit 10` の結果も見せる。
  - **既存の Issue に着手する** → 番号を聞いて「A. 既存 Issue」へ
  - **新しく起票する** → 「B. 新規起票」へ

`/issue <番号>`（`12`・`#12`）または `/issue <このリポジトリの Issue の URL>` で始めたときは、`UserPromptSubmit` フック（`.claude/hooks/set-issue-session-title.sh`）がセッション名を `#<番号>-<先頭の [...] を 1 つ除いたタイトル>`（除くと空になるときは `#<番号>`）に設定する。実行のたびに上書きする。スキル側で名前を付ける操作は要らない。引数なしで始めたときは付かない。フックには `gh` と `jq` が必要で、取得に失敗したときは名前を付けずにそのまま進む（その場合もスキル側では名前を付けない）。

## ① 要件定義

### A. 既存 Issue

1. `gh issue view <番号> --comments` で本文とコメントを読む
2. ステータス欄があれば現在の工程を読み、AskUserQuestion で「続きから再開（推奨）」か「①からやり直す」かを選んでもらう。続きからなら該当する工程へ進む
   - ③以降から再開するときは、作業ブランチ名をステータス欄（なければ③の工程コメント）から読む。`git status -sb` で今のブランチと未コミットの変更を確認する。すでに作業ブランチにいれば、未コミットの変更はこの Issue の作業内容として扱い、確認は不要。別のブランチにいて未コミットの変更があるときだけ、どう扱うかユーザーに聞く。そのうえで `git switch <ブランチ名>` で作業ブランチに切り替える。切り替えられなければ（作業ブランチがローカルにないなど）ユーザーに知らせる
   - ④以降から再開するときは、`git status --short -uall`（未追跡ファイルを含む）と `git diff --name-only develop...HEAD` の結果を合わせて、変更ファイルの一覧を作り直す（`git status` の出力は先頭の状態記号を除き、名前の変更（`R 旧 -> 新`）は変更後のパスを使う）
3. ステータス欄を「① 要件定義中」に更新する。本文にステータス欄がなければ、ここで挿入する
4. `doc-reviewer` に Issue の本文を渡し、要件の抜け漏れ・曖昧さ・現在のコードとの食い違いをレビューさせる
5. 要件の要約（やること／やらないこと／完了条件）と `doc-reviewer` の指摘をユーザーに見せ、要件を確定させる。確定するまで次に進まない
6. 確定した要件が Issue 本文と違う場合は、その差分を①の工程コメントに書く
7. ①の工程コメントを追加・更新し、ステータス欄を「① 要件定義済み」にして要約と①の印を書いてから「② 設計」に進む（②に入ったときに「② 設計中」にする）

### B. 新規起票

**ユーザーが要件を了承するまで Issue は起票しない。**

Issue テンプレートは `.github/ISSUE_TEMPLATE/` にある。現在のテンプレート:

!`ls .github/ISSUE_TEMPLATE`

1. 何を起票したいかユーザーに聞く（不具合か機能追加か、内容、再現手順や期待する動き）。あわせて、既存の Issue（親 Issue）から切り出すものかも聞く。ユーザーの話から親 Issue が分かるときはそれを使い、合っているか確認だけする
2. 内容に合うテンプレートを選んで Read する。各テンプレートの frontmatter の `name`／`about` で判断し、どれに当たるか迷うときはユーザーに聞く
3. 必要に応じて関連コードを調べ、原因の候補や影響しそうなファイルを把握する。親 Issue があるときは、必ず次も行う
   - `gh issue view <親の番号> --comments` で親の本文とコメントを読み、親の要件のどの部分を切り出すのかを踏まえて案を作る。親の範囲を超えないこと、親や既存のサブ Issue と内容が重複しないことに気を付ける
   - 既存のサブ Issue は `gh issue view <親の番号> --json subIssues` で一覧を取り、必要なものは `gh issue view <番号>` で中身を読む（`gh api` は使わない）
   - 親が閉じているとき、またはこのリポジトリの Issue ではないときは、ユーザーに確認する。`--parent` に渡す値と本文の `#<番号>` は、このリポジトリの Issue 番号にそろえる（URL を渡されたら番号に直す）
4. テンプレートに従ってタイトルと本文の案を日本語で作る
   - **タイトル**: frontmatter の `title`（例: `[バグ] `、`[Feature] `）を先頭に付ける
   - **本文**: テンプレートの見出し（`## 〜`）を同じ順番ですべて残し、各見出しの下を埋める
     - 本文の最上部にはステータス欄（「Issue の進捗記録」）を入れる。ステータスは「① 要件定義済み」にし、要約を書いて①に印を付ける
     - `<!-- -->` のコメントは書き方の指示として読み、本文からは消す（ステータス欄のマーカーは残す）
     - 書くことがない見出しは消さず、テンプレートにある既定の文（例: 「特に無し」）を残すか「特に無し」と書く
     - 「関連Issue」のチェックリストは、関連する Issue があれば `- [ ] #<番号>` の形で書き、なければ空の項目を消して「特に無し」と書く。親 Issue があるときは必ず `- [ ] #<親の番号>` を書く（「（親 Issue）」のように親であることを書き添えてよい）
     - 調べて分かった関連ファイルは、「補足」（機能の場合は「設計方針」でもよい）に `[ファイル名](パス)` の形で書く
   - **ラベル**: frontmatter の `labels` をそのまま使う
5. `doc-reviewer` に起票案とテンプレートのパスを渡し、要件の抜け漏れ・曖昧さ・コードとの食い違い・テンプレートとの不一致をレビューさせ、指摘を案に反映する（最上部のステータス欄はテンプレートとの不一致として扱わないよう伝える）。親 Issue があるときは、`doc-reviewer` は gh を実行できないので、親の番号と内容（本文・コメントの要点）と、手順 3 で取った既存のサブ Issue（番号・タイトル・要点）も渡し、親の要件の範囲を超えていないか、親や既存のサブ Issue と重複していないかも見させる
6. タイトル・ラベル・本文の案と、反映した指摘の要約をユーザーに見せ、要件の了承を取る。親 Issue があるときは、どの Issue のサブ Issue として起票するかも案に含める。修正を求められたら、親 Issue を変えるとき・新しく付けるとき・外すときは 3〜6 を、それ以外の修正は 4〜6 を繰り返す
7. 了承されてから初めて起票する。本文を一時ファイル（「Issue の進捗記録」）に書き出し、`gh issue create --title "<タイトル>" --body-file <一時ファイル> --label "<ラベル>"` で起票して Issue の URL を報告する（ラベルが複数あるときは `--label` を繰り返す）。起票したら、続けて①の工程コメントを追加する
   - 親 Issue があるときは、`gh issue create --title "<タイトル>" --body-file <一時ファイル> --label "<ラベル>" --parent <親の番号>` で親のサブ Issue（GitHub の sub-issue）として起票する。起票後、`gh issue view <新しい番号> --json parent --jq .parent.number` で親の番号が返ることを確かめる
   - Issue が作られなかったとき（`--parent` を受け付けないなど。gh の出力に Issue の URL がない）は、出力に URL がなくても、`gh issue list --state open --search "<タイトル> in:title" --limit 5` で同じタイトルの Issue がないか確かめる。見つかったら、作られたものとして次の項目（作られたが紐付けを確認できないとき）の扱いにする。見つからなければ、起票し直す前に AskUserQuestion で「gh を更新してから起票し直す（推奨）」「親を付けずに起票し、紐付けはユーザーが GitHub の画面で行う」「起票を中止する」から選んでもらう
   - Issue は作られたが紐付けを確認できないときは、起票し直さない。Issue の URL を報告し、紐付けはユーザーに GitHub の画面で行ってもらう。①の工程コメントは、紐付けの成否と関係なく追加する
   - どちらの失敗のときも、ユーザーの判断を待つ。起票し直すときは手順 7 をやり直し、Issue ができたら手順 8 に進む。中止したときはここで終える
   - 親 Issue には、本文・ラベル・ステータス欄の変更もコメントも含めて、何も書き込まない。必要に見えるときはユーザーに確認する
8. そのまま着手するかユーザーに聞く。着手するなら、確定した要件のまま「② 設計」に進む

## ② 設計

1. `planner` に確定した要件と Issue 番号を渡し、影響範囲・変更するファイル・実装手順・懸念点を整理させる。変更するファイルは、コードとドキュメント（作成・更新が必要なもの）を分けて挙げさせる。設計に関わる変更なら `docs/architecture.md` と CLAUDE.md の設計方針を踏まえるよう伝える
2. 設計の要約をユーザーに見せ、了承を取る
3. ②の工程コメントを追加・更新し、ステータス欄を更新してから実装に進む

## ③ 実装

手順 1・2 は、この Issue の作業ブランチがまだないときだけ行う。②・⑤から戻ってきたときは手順 3 から始める。

1. `git status` で未コミットの変更がないか確認する。あればどう扱うかユーザーに聞く
2. `develop` に切り替えて `git pull` で最新にし、そこから作業ブランチを作って切り替える（`git switch -c <ブランチ名>`。開発の起点は `develop`。`main` は使わない）
   - バグの Issue（`bug` ラベルが付いている、またはタイトルが `[バグ]` で始まる）→ `bug/<番号>-<修正内容>`
   - それ以外 → `feature/-<番号>-<修正内容>`
   - `<修正内容>` は内容を表す英語の kebab-case で、20文字まで（例: `bug/fix-mmd-load-error-12`）
   - ブランチを作ったら、ブランチ名をステータス欄と③の工程コメントに書く
3. 次を**並行して**起動する。どちらかの変更がなければ、そのエージェントは起動しない
   - `implementer`: 確定した要件と `planner` の設計を渡してコードを実装させる（`.claude/rules/` のルールに従う。lint・型チェック・フォーマットまで確認させる。ドキュメントは編集させない）
   - `doc-writer`: 確定した要件と `planner` の設計のうち、作成・更新するドキュメントを渡して書かせる
4. 両方が報告した変更ファイルの一覧（リポジトリルートからのパス）を控える。`doc-writer` が「実装と照らし合わせて確認が必要」とした箇所は、④の `doc-reviewer` に伝える。`implementer` の報告にドキュメントの更新が必要な点があれば、`doc-writer` に依頼してから④に進む（その変更ファイルも一覧に加える）
5. 変更ファイルの一覧と実装内容の要約をユーザーに見せ、了承を取る
6. ③の工程コメントを追加・更新し、ステータス欄を更新してから④に進む

## ④ レビュー

1. 変更が CLAUDE.md の「サブエージェントの使い方」にある軽微な修正の基準に当たるか判断する。当たるときは、軽微なのでレビューを省くことを、理由を添えてユーザーに伝える。迷ったら軽微として扱わない
2. 確認を始める
   - 軽微でないとき: `code-reviewer` と `quality-checker` を**並行して**起動し、両方に変更ファイルの一覧を渡す。ドキュメントを変更していれば `doc-reviewer` も同時に起動する。コードを変更していなければ `doc-reviewer` だけを起動する
   - 軽微なとき: レビュー（`code-reviewer`・`doc-reviewer`）は省き、機械的な確認だけを行う。コードを変更していれば `quality-checker` に変更ファイルの一覧を渡して起動する
   - どちらの場合も、ドキュメントを変更していれば、メインが `pnpm --dir app exec prettier --check --config .prettierrc.json <変更したドキュメント>` を実行する（パスは `app/` からの相対パス。`app/` の外のファイルには設定が自動で適用されないため `--config` を付ける）。整形エラーは指摘として扱う
3. どれかで指摘があれば、内容をまとめて修正を依頼する（コードは `implementer`、ドキュメントは `doc-writer`。`code-reviewer` などから出たドキュメントの不足・誤りの指摘も `doc-writer` に回す。両方あれば並行して）。修正案から外れた箇所があれば報告するよう伝える。修正後は、修正で変更したファイルに応じて機械的な確認（コードなら `quality-checker`、ドキュメントならメインの `prettier --check`）をやり直し、起動したエージェントすべてに再確認させる。ただし、すべての修正が修正案どおりで、今回の修正が CLAUDE.md の「軽微に含めないもの」に当たらなければ、ユーザーに伝えたうえで再レビュー（`code-reviewer`・`doc-reviewer`）を省く。機械的な確認は省かない（修正案のない指摘を直したときは修正案から外れたもの、`prettier --write` で直せる整形だけの修正は修正案どおりとみなす）。手順 1 でレビューを省いていても、今回の修正が軽微な修正の基準に当たらないとき（「軽微に含めないもの」に当たるときを含む）は、手順 2 の「軽微でないとき」の構成でレビューを起動する
4. 指摘がなくなるまで繰り返す。繰り返すたびに④の工程コメントを更新する
5. レビュー結果の要約（出た指摘と直した内容。レビューを省いたときはその旨と理由）をユーザーに見せ、了承を取る
6. ④の工程コメントを追加・更新し、ステータス欄を更新してから⑤に進む。レビューを省いたときは、省いた理由を④の工程コメントに書く

## ⑤ 動作確認

1. `app/` 配下の変更したファイルだけを対象に、最終確認として lint とフォーマットを確認する（パスは `app/` からに直して渡す。型チェックは④で済んでいるので行わない。`app/` の外のドキュメントは④でメインが `prettier --check` 済み）
   - `pnpm --dir app exec eslint <変更した .ts/.tsx>`
   - `pnpm --dir app exec prettier --check <変更したファイル>`
   - エラーがあれば修正させ、④の手順 3（修正後の再確認）から再開する。コードのエラーは `implementer` に修正させる。`.md` の整形エラーは、メインがエラー内容（該当ファイルと箇所）を `doc-writer` に渡して直させる
2. ユーザーに次をまとめて報告する
   - レビュー結果とチェック結果の要約
   - **ユーザーが画面で確認すべき箇所**: `pnpm --dir app run dev`（`http://localhost:3000/web-game-engine/`）で開いたあと、どの画面・パネルで、どう操作し、何が見えれば正しいか。UI に影響しない変更なら「UI の確認は不要」と理由付きで書く
3. ユーザーが UI を確認して問題がないと答えるまで待つ。問題があれば内容を聞いて③に戻る（設計から見直す必要があれば②に戻る）
4. ⑤の工程コメントを追加・更新し、ステータス欄を更新してから PR 作成に進む

## PR 作成

1. 変更内容の要約と差分をユーザーに見せ、コミット・push・PR 作成の了承を取る
2. 了承されたら、日本語のメッセージでコミットし、push して `gh pr create --base develop` で `develop` 向けの PR を作る。PR 本文には `Closes #<番号>` と変更の要約を書き、一時ファイル（「Issue の進捗記録」）に書き出して `--body-file` で渡す
3. PR 作成の工程コメントを追加・更新し、ステータス欄を「PR 作成済み」にして PR へのリンクを書く
4. 作成した PR の URL を報告し、ほかに対応が要らないかユーザーに確認する
